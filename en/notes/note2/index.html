WiredTiger: Write Conflicts Under High Concurrency

2025-04-12
databasesmongodbsystemsconcurrency

Notes from production debugging with 3 000+ MongoDB databases on a single replica set.

Background

MongoDB’s WiredTiger storage engine uses MVCC (Multi-Version Concurrency Control) with snapshot isolation. Every transaction sees the state of the database as of its start timestamp — writes from concurrent transactions are invisible until they commit.

What is a Write Conflict?

A write conflict occurs when transaction T2 attempts to modify a record that transaction T1 has already modified but not yet committed:

T1: BEGIN ──UPDATE doc A ──────────────────COMMIT
T2: BEGIN ─────────────────UPDATE doc A ──► WT_ROLLBACK

WiredTiger detects this optimistically and returns WT_ROLLBACK, which MongoDB surfaces as:

WriteConflict error: write conflict (WT_ROLLBACK)

Root Cause in High-DB-Count Deployments

With 3 000+ databases, the WiredTiger checkpoint thread periodically flushes all dirty pages, creating a burst of write I/O competing with eviction threads and live application writes.

db.serverStatus().wiredTiger.transaction
// {
//   "transaction begins": 18423991,
//   "transactions rolled back": 94812,   // ← spike here
//   "write conflicts": 94101
// }

Tuning

1. Increase eviction thread count

db.adminCommand({
  setParameter: 1,
  wiredTigerEngineRuntimeConfig:
    "eviction=(threads_min=4,threads_max=12)"
})

2. Raise eviction dirty trigger

db.adminCommand({
  setParameter: 1,
  wiredTigerEngineRuntimeConfig:
    "eviction_dirty_trigger=15,eviction_dirty_target=10"
})

3. Spread checkpoint I/O

# mongod.conf
storage:
  wiredTiger:
    engineConfig:
      checkpointSizeMB: 512

Result

After tuning, write conflicts dropped by ~87% and p99 operation latency fell from 340 ms to 38 ms on the affected replica set.
