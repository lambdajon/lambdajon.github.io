Journaling in Filesystems: fsync, WAL, and Crash Consistency

2025-03-08
filesystemssystemsstorage

Overview

Crash consistency is one of the oldest unsolved problems in systems software. When power fails mid-write, a filesystem must ensure it can recover to a consistent state. This note surveys the main techniques.

fsync and the Write Ordering Problem

A naive approach: write data first, then update metadata.

write(fd, data, len);   // data block written
fsync(fd);              // flush to disk
update_inode(inode);    // now update metadata

Without ordering guarantees this is still unsafe — the OS may reorder writes and the inode update can land before the data block, leaving a pointer to garbage.

Write-Ahead Logging (WAL)

WAL (used by ext3/4, XFS, btrfs) writes a journal record before modifying the actual filesystem structures:

┌────────────────────────────────────────────────────────┐
│  Journal                                               │
│  [TxBegin | inode-update | data-block | TxCommit]      │
└───────────────────────┬────────────────────────────────┘
                        │  only after TxCommit is durable
                        ▼
                  Filesystem blocks

On recovery, the journal is replayed from the last committed transaction — any incomplete transaction is simply discarded.

Journaling Modes (ext4)

Mode What is journaled Performance Safety
data=journal Data + metadata Slowest Highest
data=ordered Metadata only (data flushed first) Default Good
data=writeback Metadata only Fastest Weakest

Copy-on-Write (btrfs, ZFS)

CoW filesystems never overwrite data in place. Every write goes to a new location; the old block remains intact until the new one is durably committed:

Old tree:  [root] → [node A] → [leaf X]
Write X':  [root'] → [node A'] → [leaf X']   (new path)
           old path still intact until root' is committed

This makes crash consistency almost free — an interrupted write simply leaves the old tree valid.
